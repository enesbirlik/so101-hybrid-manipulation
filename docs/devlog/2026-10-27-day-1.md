# Day 1 — Bus driver, joint calibration & live RViz view

**Date:** 2026-10-27 · **Roadmap step:** 3. Calibration, URDF matching, fisheye camera calibration · **Status:** joints done, one open problem

The goal for this step was for the real arm and its URDF model to agree. When a joint on the real arm sits at 30°, the model in RViz should show 30° in the same direction.

## What I did

- Added the arm model as the [`so101_description`](../../so101_description/) package. The URDF and meshes come from TheRobotStudio/SO-ARM100. The wrist camera became an optional xacro macro, and the package has an RViz display launch.
- Replaced the day-0 throwaway script with proper tools in [`tools/`](../../tools/):
  - `feetech_bus.py`: a minimal driver for the Feetech STS serial protocol, built on pyserial. It opens only the servo board's USB adapter, with an exclusive lock.
  - `so101_calibrate.py`: calibrates one joint at a time with torque off.
    1. Move the joint by hand to both ends of its range.
    2. Hold it at the URDF zero pose (or use a hard stop as the zero) and press Enter.
    3. The tool writes the homing offset and position limits to the servo's EEPROM, reads them back to check, saves them to the calibration file and locks the joint.

    It also has `scan`, `live`, `check`, `zero` and `off` commands.
  - `so101_joint_states.py`: publishes the real joint angles on `/joint_states`, so RViz shows the real arm live.
  - `so101_teleop.py`: jogs the joints from the keyboard. Goals are clamped to the calibrated range, and a watchdog freezes the arm when a joint falls behind its goal.
- Calibrated all six joints. Their directions match RViz, and all are +1. The result is in [`so101_bringup/config/so101_calibration.yaml`](../../so101_bringup/config/so101_calibration.yaml):

  ```
  joint_rad = direction * (ticks - zero) * 2*pi / 4096
  ```

## What I learned

- The ST3215 encoder is absolute within one turn, and the homing offset is stored in EEPROM. Calibration is therefore a one-time step. At each startup the tools only check that offsets and positions still match.
- A hard stop is a better zero reference than a pose held by hand, because it is exactly the same every time:
  - `elbow_flex`: folded stop at +91.8°.
  - `gripper`: closed stop at −10°.
- The upstream URDF elbow limit (+96.8°) is about 5° wider than the real mechanical stop. Do not treat URDF limits as measurements.
- The order of joint moves matters. When the folded arm moves all joints to zero at once, the forearm sweeps into the table.

## Problems & fixes

| Problem | Cause | Fix |
|---|---|---|
| Folded elbow meshes overlapped in RViz | Zero taken against the URDF limit (+96.8°) instead of the real stop | Zero elbow from the folded hard stop (+91.8°), recalibrate |
| Forearm pushed into the table on "go to zero" | All joints moved together | Staged zero: `shoulder_lift`, then `elbow_flex`, then the rest |
| One corrupted reply aborted the whole tool | No retry on bad checksum | Retry each bus transaction once |
| A second tool crashed with a traceback | Port already locked by another tool | One-line "port busy" error |
| Arm could not hold itself horizontal | Torque limit at 70 % | Moves now use 100 % |
| **Open:** with torque on, `shoulder_lift` and `elbow_flex` jerk into their stops (overcurrent trip, ~2.5 A) | Suspected: horns were not mounted at servo centre, so the raw encoder wrap falls inside some joint ranges and the servo's position loop drives the wrong way. **Not verified yet.** | Test planned. If confirmed: re-centre the servos, remount the horns, recalibrate those joints |
