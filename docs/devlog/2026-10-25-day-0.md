# Day 0 — Hardware & first motor test

**Date:** 2026-10-25 · **Roadmap step:** 1. Parts, BOM & 3D prints → 2. Assembly & first motor test · **Status:** done

Starting point of an open build log: building an SO-101 arm and using it to study when a classical planner should hand over control to a learned policy. See the [README](../../README.md) for the full research question.

## What I did

- Collected the parts and 3D-printed the SO-101 follower arm parts:

  | Component | Details | Qty |
  |---|---|---|
  | Servos | Feetech ST3215, 12 V serial bus servo | 6 |
  | Servo driver | Waveshare bus servo driver board (USB) | 1 |
  | Power supply | 12 V 10 A constant-voltage | 1 |
  | Camera | USB, 32×32 mm module, 135° wide-angle lens, wrist-mounted | 1 |
  | Structure | 3D-printed SO-101 parts | 1 set |

- Assembled the arm and powered the servo bus.
- Wrote a quick throwaway Python script (pyserial only) to talk to the servos directly over the Feetech protocol at 1 Mbps:
  - pinged every ID on the bus to find which servos respond,
  - read present position, voltage, and temperature from each one,
  - assigned IDs one motor at a time (unlock EEPROM → write ID → lock again),
  - ran small test moves around the current position with torque switched off at the end.
- Result: the servos respond on the bus and move on command. Proper measurements (bus voltage under load, per-joint ranges) come with the bring-up tool and calibration.

## What I learned

- Bus servos share one data line, so every servo needs a unique ID **before** the arm is assembled; IDs have to be set with only one servo connected.
- ID and other configuration values live in EEPROM and are write-protected by a lock register; runtime values like goal position live in RAM.
- Position is reported in ticks (0–4095 for a full turn), so converting to joint angles needs a per-joint offset and direction. That is the job of phase 3 calibration.
